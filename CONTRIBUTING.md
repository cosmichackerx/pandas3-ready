# Contributing

* A new rule needs an entry in `src/pandas3_ready/rules.py`, a detector in `analyze.py`, unit tests with positive **and negative** cases (other libraries that share the method name: numpy, torch, str), and oracle cases in `tests/oracle/cases.py`.
* Every rule that claims "pandas 3 raises / changes / warns on X" must be an oracle case run on real pandas 2.3.3 and 3.x: create two virtualenvs (`pandas==2.3.3` and `pandas==3.0.6`, plus `lxml`), run `python tests/oracle/run_oracle.py --exec out.json` with each, then `python tests/oracle/run_oracle.py old.json new.json`. If a behaviour cannot be checked that way, say so in the README table instead of adding an oracle flag.
* Precision first: a detector must say how it knows the code is pandas (`high` provably, `medium` vocabulary, `low` shape). A method name that numpy, torch or `str` also have is only allowed on a provably-pandas receiver.
* When a new pandas release changes a behaviour, extend `NEW` in `rules.py` and the CI matrix, re-run the oracle and update the README. Do not widen a claim to versions that were not run.
* Keep the project dependency-free (standard library only) and compatible with Python 3.9. `src/pandas3_ready/names.py` is generated by `tools/gen_names.py`.
* Releasing: bump the version and the README pins in a PR, merge when green, then run **Actions > Release gate** with the new tag (for example `v1.2.3`) *before* you create the tag. The same check runs again on the tag, and a weekly job (`claims-latest.yml`) fails when the README pins an older release than the newest tag.
